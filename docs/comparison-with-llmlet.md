# llmletとの差分・比較

[llmlet](https://github.com/ktock/llmlet)は設計の土台にした先行事例。

## 共通点(llmletから受け継いだ/独自検証で同結論)

- WASM版llama.cpp + WebGPU(またはCPUフォールバック)
- RPCバックエンドへのパッチでブラウザピア同士がWebRTC経由認識
- クライアント役ピアがモデルロード・チャンク配布・推論仲介(星型トポロジー)
- 1クライアント固定制約

## 差分

| 項目 | llmlet | 今回 |
|---|---|---|
| シグナリング | 外部PeerJS公開サーバー(README曰くTURN未提供のため制限環境で接続不可の場合あり) | 自前Hono、LAN内完結、インターネット不要 |
| ピアの動的増減 | 明示的設計なし | generation番号による再構成(生成中は現編成のまま完走、次生成から反映) |
| 想定開発体制 | 個人/少人数(型定義・責務分担ドキュメントなし) | 4人チーム(初心者2人)。`packages/shared-types`で型共有、モックによる並行開発 |
| UI | シンプルなテキストエリア | requester用チャットUI + peer用貢献演出UIを分離 |

## LAN限定を活かせる差分

**低リスク(現設計にそのまま乗る):**
- セキュリティ考慮省略: llama.cpp公式RPC READMEはRPCサーバーを開放ネットワークで動かすなと明記。llmletは不特定多数向けのため対策が要るが、閉じた会場LANで数時間動けばよい今回は正当にスキップ可能
- 接続信頼性ほぼ100%: llmletはTURN未提供のため制限環境で接続失敗の可能性ありと明記。同一LAN・同一APならこの失敗モードが消える
- QRコード1枚で参加者を増やす演出: 会場にいる人が同じ部屋にいる前提を活かせる。離れた場所を繋ぐことが本質のllmletにはできない見せ方

**中リスク(要検証):**
- モデル配布速度: LAN帯域はインターネット経由(特にTURN中継時)より太く安定。ただし会場Wi-Fi混雑次第

**高リスク(時間との相談):**
- 真の並列化: llmletのKnown limitationsは並列化未対応・逐次評価で通信オーバーヘッド発生と明記(インターネット越し遅延前提の同期コストが理由と推測)。LAN内は遅延が1桁小さく同期コストが許容範囲に収まる可能性。実現できれば性能面で明確に上回るが、llama.cpp RPC実装自体の改造が必要になり得るため①の作業量が跳ね上がる。時間が余れば挑戦する拡張枠として扱う

## 正直に認めるべきllmletの優位点

- 既に動くものが存在する(今回は未実装、1日目検証が最大リスク)
- RPCのWebRTCパッチを書き終えている(今回はベースにできるがシグナリング差し替え等が残る)
- 構成要素が少なくシンプルで壊れにくい(今回はHono・シグナリング中継・世代管理など可動部品が多い)

差分をつけること自体を目的化せず、「今回の要件(チーム開発・LAN完結・動的増減)に対応するために本当に必要か」を都度確認する。
