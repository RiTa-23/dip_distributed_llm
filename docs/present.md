# プロジェクト紹介

## 簡単な紹介

### 簡単に説明(32文字以内)

参加者のPCを束ねて動く分散LLM推論システム

### 作った背景(140文字以内)

1台のPCには載らない大きなLLMも、会場にいる参加者のPCの計算資源を少しずつ借りれば動かせるのでは、という発想から生まれました。ハッカソンという「その場に人が集まる」場だからこそ成立する、モデルの重みも計算も会場LANから出さない分散推論に挑戦しています。

### 推し技術(140文字以内)

制御はHono(WebSocket)、実データはWebRTC DataChannelで直接P2Pという2層構成が肝です。Honoはロスター管理と合図に徹し、推論のデータを経由しません。ブラウザで動くWASM版llama.cppと組み合わせ、インストール不要で計算に参加できます。

### 推しアイディア(140文字以内)

観客のノートPCが、その場でモデルの一部として組み込まれていく体験そのものが本命のアイデアです。QRコードをスキャンして参加した瞬間、自分のPCがAIの計算を肩代わりし始める様子を、会場全員が目撃できるライブ感を大事にしています。

## プロジェクト概要

### 概要

会場LAN内で、複数のブラウザ(PC)の計算資源を束ねて1つの大きなLLMを分散推論させるハッカソンプロジェクトです。

- **requester**(推論をリクエストする側・同時1人固定): プロンプトを入力し、生成結果を受け取る発表者用の画面
- **peer**(計算資源を貸す側・複数・QRコードで随時参加): 自分のPCの空き時間を推論の一部に貸し出す参加者用の画面

参加PCが増えるほど、1台では動かせない大きな/賢いモデルが動くようになります。参加は「QRコードを読み取ってブラウザでページを開くだけ」で、アプリのインストールやアカウント登録は不要です。

### 使用技術・技術選定の理由・アーキテクチャ

**技術スタック**

| レイヤ | 技術 | 役割 |
|---|---|---|
| フロントエンド | React + Vite + Bun | requester画面(チャットUI)・peer画面(貢献演出UI) |
| バックエンド | Hono + Bun | ロスター管理・WebRTCシグナリング仲介・静的配信 |
| 制御プレーン | WebSocket | 軽量な状態同期(誰が参加しているか・生成開始合図) |
| データプレーン | WebRTC(DataChannel) | requester⇔peer間のRPC(テンソル)をP2P直接転送 |
| 推論エンジン | llama.cpp(RPCモード) + WebAssembly | ブラウザ内で動く分散推論エンジン本体 |

現在のモデルは `qwen2.5-0.5b-instruct-q4_k_m.gguf`(約491MB)です。requesterのRuntimeがHonoから1回ダウンロードし、各peerへはWebRTC経由でテンソルが流れます。peerがモデルファイルを持つ必要はありません。

**アーキテクチャ上の3つの柱**

1. **星型トポロジー**: requesterが全peerと個別にWebRTC接続する構成です。llama.cppのRPCアーキテクチャ自体が星型のため、peer同士が直接通信する必要はなく、peer間の接続は確立しません。

2. **制御プレーンとデータプレーンの分離**: Hono(`/ws`)が扱うのは「誰が参加しているか」「いつ生成を始めるか」といった軽量なJSONだけです。推論中のテンソルは一切Honoを経由せず、requester⇔peer間のWebRTC DataChannelで直接P2P転送します。Honoが重いデータを中継すると、会場の無線LAN区間を実質2回通過することになりボトルネックになるため、設計段階でこの分離を最優先しました。

3. **世代(generation)ベースの動的再構成**: 参加者は会場の性質上、途中からどんどん増えていきます。ピアの増減は「次の生成が始まるタイミング」でのみ編成に反映し、生成中にトークン単位で編成を変えることはしません。実装を進める中で、この柱を支えるメッセージが3つ増えました。

   - `requester_accepting` … 推論の最中に新しい参加者が来たとき、いま取り込んでよいかを発表者側が制御する。断っている間は溜めておき、許可した瞬間にまとめて1回だけ再編成する
   - `generation_failed` … 編成したものの接続できなかったことをHonoへ伝える。これが無いと、誰かが切断するまでサーバーが「生成中」のまま固まる
   - `generation_aborted` の理由 … 「人が増えた」「人が減った」「接続に失敗した」を区別して画面に出し分ける

   当初は「増減したら組み直す」だけの想定でしたが、**実際に動かすと「組み直せないまま固まる」経路が見つかり**、それを塞ぐ形で契約が育ちました。

**飛び入り参加のための証明書設計**

ブラウザでWASM版llama.cppを動かすには、pthread(`SharedArrayBuffer`)のためにHTTPSと COOP/COEP ヘッダが要ります。ところが開発用のmkcert証明書は、rootCAを入れた端末でしか信頼されません。**会場で飛び入り参加する他人のPCには証明書警告が出てしまい、「QRを読むだけで参加」というUXが崩れます。**

そこで、実在ドメインに対して Let's Encrypt の証明書を DNS-01 方式で取得し、そのドメインのAレコードが**会場LANのプライベートIP**を指す構成にしました。DNS-01 はTXTレコードを一時的に置けるかだけを検証するため、サーバーが外部から到達可能である必要がありません。

この構成で外に出るのは「ドメイン名 → 会場のLAN IP」の名前解決だけです。**モデルの配布も推論のテンソルも制御メッセージも、会場LANから出ません。**

**先行事例との関係**

WASM版llama.cpp + WebRTCによるブラウザ分散という土台は、既存プロジェクトllmletを参考にしています。差分として、シグナリングを外部の公開PeerJSサーバーに依存せず自前のHonoで完結させた点、上記の世代番号による動的な再構成の仕組みを追加した点が挙げられます。

**技術選定の理由(抜粋)**

- **Bun**: TypeScriptをそのまま実行でき、Bun workspacesでモノレポ(フロント・バックエンド・共通型定義)を1つの`bun install`で管理できるため採用しました。
- **Hono**: フロントと同じTypeScriptで書け、静的配信とWebSocketの両方を1つのアプリでシンプルに扱えるため採用しました。当初は「重いデータをサーバーが中継するならGoが有利では」という案もありましたが、実データをWebRTCで直接P2P転送する設計に変更したことで、Honoが扱うのは軽量なJSONだけになり、言語間のパフォーマンス差は問題にならなくなりました。
- **WebRTC**: ブラウザ間で直接P2P通信できる標準技術はこれしかありません。同一LAN内であればSTUN/TURNサーバーは不要ですが、会場Wi-Fiが端末同士の通信を遮断している場合に備え、**会場LAN内に自前で立てたTURNを使える設定**も用意しています(外部のTURNサービスには依存しません)。

### 開発の進め方の工夫

**開発を始める前の土台づくり**

- **Bun workspacesでReact + Honoのモノレポ構成**: `apps/web`(React)・`apps/server`(Hono)・`packages/shared-types`(共通型定義)を1つのリポジトリに集約し、`bun install`一発で依存解決できる構成にしました。フロントとバックエンドで言語・パッケージマネージャーが分かれないため、担当を跨いだキャッチアップコストが低いのも利点です。
- **CI(lint / format / test / typecheck)を最初から整備**: GitHub Actionsを組み、モノレポの変更箇所に応じてジョブをパスフィルタで分岐させ、無駄なCI実行を減らしています。現在はフロント207件・バックエンド169件のテストが通っています。
- **AI用ドキュメント・skillsの整備**: `AGENTS.md`にAIコーディングエージェント向けの前提情報(アーキテクチャ制約・ディレクトリ構成・コーディング規約)を一元化しました。さらに「docsとコードの実装が食い違っていないかを機械的にチェックする」skillも用意し、AIに開発を任せる場面でも設計判断がぶれないようにしています。
- **Notionで開発用ドキュメントを共有**: 会議メモや設計の検討過程など、リポジトリのコードに残すには重すぎる情報はNotionに集約し、GitHub側のドキュメントとは役割を分けました。
- **Discordをチャンネル分けして活用**: GitHubのPR/Issue通知をWebhookで流すチャンネル、各種リンクにすぐアクセスできるチャンネル、参考記事を投げられるチャンネルなど用途別に分けました。

**契約を先に決めて、担当ごとに独立して進める**

- **WebSocketのメッセージ契約を事前に定義**: 実装に入る前に、やり取りするメッセージの型を`packages/shared-types`に判別可能ユニオン型として固め、`docs/api-contract.md`にも明文化しました。これにより、担当分野に関係なく、それぞれが契約だけを頼りに独立して開発を進められました。
- **モックファースト開発**: フロント側は、本物のWebSocket接続と同じ返り値の形を持つモックを最初に作り、バックエンド完成前から画面遷移や状態管理を作り込めるようにしました。
- **状態を1つのreducerに集約**: 参加者・発表者どちらの画面も「7つの状態のうちどれか1つ」という直和型で管理し、状態遷移ルールを1ファイルに閉じ込めました。「繋がっていないのに貢献中」のようなありえない状態を型のレベルで作れないようにしています。
- **Issueをフェーズ分割して段階的に実装**: 作業をフェーズ分けし、親issueとサブissueで進捗を追えるようにしました。1つの機能追加ごとにブランチを切ってPRを作成し、CodeRabbitによる自動レビューと人手のレビューの両方を通してからマージする運用です。

**途中で分かったことを、運用に反映していく**

- **一番重い依存を待たずに進めるための「代役」**: WASM版llama.cppのビルドは最難関で、完成を待つと他の作業が全部止まります。そこで、**C側と同じ呼び出し方をする偽物**を先に用意し、その上でDataChannelとRPCの橋渡しだけを確定させました。実際のDataChannel上で16MiBのデータ往復がバイト単位で一致することまで確認してあり、本物が到着したときには差し込むだけで済む状態を作れました。
- **契約を変えるときは、サーバーとフロントを同じPRで直す**: あるとき、サーバー側だけ新しい種別を送るようにしたところ、フロントの検証リストに無い値だったため**メッセージが黙って捨てられる**という事象が起きました。以降は、型定義・サーバー・フロント・ドキュメントを1つのPRで揃える運用にしています。
- **手元に無い環境を「対応済み」と書かない**: Windows対応を実装した際、macOSしか手元に無かったため「Windows未確認」と明記してレビューに出しました。Windows実機を持つメンバーが検証して、証明書のSAN・セットアップの完走・COOP/COEPの付与まで確認したうえでマージしています。同時に見つかった別の不具合も、その場でissueとして切り出しました。
- **担当の境界を、実態に合わせて引き直す**: 当初は「フロントはDataChannelが開くところまで、その先のRPCはコア担当」という分担でしたが、進めるうちに**WebRTCはシグナリングからRPCの繋ぎ込みまで一貫して1人が持つほうが速い**と分かり、途中で境界を移しました。コア担当はWASMのビルドに集中する形にしています。

### 開発メンバー紹介(各担当について)

4人チームで、担当を分けて並行開発しました。

| 担当 | 役割 | 主な作業内容 |
|---|---|---|
| ① コア分散基盤 | 経験者・最難関領域 | WASM版llama.cppのRPCビルド・移植、WebRTC DataChannel向けのRPCパッチ、WebGPU有効化。llmletをベースに、ブラウザで動く推論Runtimeを用意 |
| ② コーディネータ/インフラ | Honoサーバー全般 | WebSocket接続管理・ロスター管理・世代ベースの再構成ロジック・WebRTCシグナリング中継・静的配信(GGUF/WASM含む)・HTTPS化と本番用証明書・Windows/macOS双方で動く開発環境整備 |
| ③ フロント(チャットUI) | requester画面 | プロンプト入力、生成結果のストリーミング表示、接続中のピア一覧、エラー表示 |
| ④ フロント(貢献側UI + WebRTC) | peer画面・データプレーン | Honoへの接続処理、貢献状況の演出、QRコードからの参加導線に加え、**WebRTCのシグナリングからRPCの繋ぎ込みまで**を担当 |

4人のうち2人はハッカソン開発が初めてのメンバーでした。①が最大のリスク要因になることが分かっていたため、初日のうちにチェックポイントを設け、②③④はモックと代役を使ってコア完成を待たずに並行して手を動かせる体制を最初から組みました。

### 現在の状況

推論Runtimeとモデルの経路はアプリケーションに統合済みで、ダミーで動かしていた部分は取り除いてあります。**複数の実機を使った通しでの動作確認は継続中**です。
